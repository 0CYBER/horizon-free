# Reference mechanism and focused feasibility

Read the explicitly requested [Noisium description](https://modrinth.com/mod/noisium) and upstream source on 2026-10-18. Its performance and parity statements are reference-author claims, not evidence for Horizon. Inspected `NoiseChunkGeneratorMixin`, `ChunkSectionMixin`, and `ChainedBlockSourceMixin` in both source branches:

- [1.20–1.20.1, c640041c8c932b36753c0ccf43902ac8b0bd252d](https://github.com/Steveplays28/noisium/tree/c640041c8c932b36753c0ccf43902ac8b0bd252d/common/src/main/java/io/github/steveplays28/noisium/mixin)
- [1.21.6, 1f9f2cb876e509130df7307d18e6dbc799875000](https://github.com/Steveplays28/noisium/tree/1f9f2cb876e509130df7307d18e6dbc799875000/common/src/main/java/io/github/steveplays28/noisium/mixin)

The placement redirect manually increments nonempty-block, nonempty-fluid, and random-ticking-block counts, obtains a palette index (which can grow/replace the backing palette storage), then writes that index into the current packed storage. It avoids obtaining/removing old-state bookkeeping and the general setter abstraction; it is not a dense chunk builder and does not omit all metadata. The later branch additionally changes section lock/unlock iteration. The sampling mixin changes the iteration over an ordered chain of material samplers (indexed list in the older branch, indexed array in the later one), preserving first non-null selection. It does not implement Horizon-style density-volume arithmetic specialization. Biome iteration changes are outside this task. No upstream code was copied into the candidate.

Horizon uses its own Java 26.3-compatible storage and generation behavior. Its noise fill already skips default air, bulk-samples density, and skips settled heightmap updates. There are no matching section locks to remove. Its generic setter maintains per-palette counts, free slots, packed widths and uniform collapse; its terrain wrapper maintains non-air counts even on existing chunks. Aquifer outputs are queried in Z/X/descending-Y order and can fail after earlier writes, so assuming that all writes merely replace fresh air would change public behavior. The direct-write idea is applicable as a private validated generation writer, not a blind replacement of the setter.

A materially different writer could pre-resolve common generated states to per-section palette tokens and write packed indices with exact counts, or buffer dense section states and construct palettes afterward. The former still needs old values/counts for nonempty input, palette growth invalidation and required terrain metadata. The latter adds roughly 384 KiB of u32 dense storage for a 384-high chunk, then scans it to build and pack palettes; retaining traversal order requires keeping multiple sections resident, and failure paths must flush exactly the earlier writes. These designs were assessed independently of the previously rejected old-state hash lookup change; that small change does not establish their speed limit. However, the profile's 6.93% inclusive setter share covers all terrain stages, so noise-only setter elimination has less whole-terrain headroom, and neither design removes the density work dominating this profile. No new direct-storage implementation was attempted.

The selected single optimization is dispatching unary density arithmetic once per bulk buffer. The measured 18.09% terrain self attribution to `UnaryOp::apply` and the actual per-element operation match provide a credible route to test. It does not change sampling calls, aquifer traversal, RNG, float expressions, buffer allocation, storage or scheduling. Scalar dispatch is retained in the scope-corrected version. Non-finite constant operands fall back to original dispatch to preserve NaN payload selection exposed by the new bit-exact differential test.
